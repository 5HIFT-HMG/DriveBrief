# 공유 뉴스 DB 연결

## 현재 RSS 기본 브리핑

기존 news_articles → Python 자동 선정·원문 구간 구성 → published_briefings의 세 옵션을 사용한다.
일반 앱은 익명 세션에서 read_published_briefing을 읽는다. 기사별 승인과 외부 LLM 호출은 없다.
세 옵션은 같은 최대 25건이며 1/최대3/최대5 구간으로 구분한다. 자동 상태는 rss_auto_validated이다.
기존 수집 동기화 성공 후 RSS 게시를 갱신한다. 출처별 TTS 이용 조건은 미확인이며 조회·QR 노출 범위는 별도 관리한다.
RSS·25건 QR 호환 SQL은 migrations/20261114_rss_auto_share.sql이다. 기존 테이블을 재생성하지 않는다.
자세한 실행·검증·운영 한계: [RSS_AUTO.md](../backend/RSS_AUTO.md).
아래 최초 설정 및 과거 검증 수치는 각 단계 당시의 기록이다.

현재 구현: Mac RSS 수집 → 로컬 SQLite 저장 → Supabase PostgreSQL 자동 동기화.
기존 자동수집 명령과 백엔드 자동수집 모두 같은 동기화 코드를 사용한다.
연결하지 않으면 기존 로컬 수집만 동작한다. 전송 실패 시 로컬 데이터를 유지하고 다음 수집 주기에 아직 성공하지 않은 변경분부터 재전송한다.
URL 기본키로 중복 삽입을 막고 기사와 분야/출처를 한 트랜잭션에서 반영한다.

## 최초 연결

간편 설정은 `news_crawler/공유DB_처음연결.command`를 실행한다. 로그인/무료 프로젝트 생성 후 URL과 Secret key를 입력하고, 자동으로 복사된 SQL을 SQL Editor에서 실행하면 설정 저장과 첫 업로드를 진행한다. Secret key는 화면에 표시하지 않으며 `.env`는 소유자만 읽고 쓰도록 저장한다.

1. https://supabase.com/dashboard 에서 무료 프로젝트를 만든다.
2. SQL Editor에서 `migrations/20261113_shared_news.sql` 전체를 실행한다.
3. `news_crawler/.env.example`을 같은 폴더의 `.env`로 복사한다.
4. 프로젝트 URL과 서버용 `sb_secret_` 키를 `.env`에 입력한다. 이 파일은 Git에서 제외된다.
5. `news_crawler/공유DB_동기화.command`를 실행한다. `synced`와 업로드 개수를 확인한다.
6. 기존 자동수집 프로세스를 한 번 재시작하면 이후 수집마다 자동 전송한다.

키는 터미널 로그, 앱 소스, APK, GitHub에 넣지 않는다.
새 Supabase secret 키는 `apikey` 헤더에만 보낸다.
환경변수가 있으면 `.env` 값보다 우선한다.

## 확인

Supabase Table Editor의 `news_articles`, `news_memberships`에서 데이터를 확인한다.
로컬 `cloud_sync_status`에는 최근 시도 상태, 업로드 수, 마지막 성공 시각이 남는다.
SQL은 재실행할 수 있다. 클라우드는 동기화마다 최근 5일·최신 1만 개 기준으로 정리한다. 로컬 원본은 이 정책으로 삭제하지 않는다.
100개씩 배치 전송하며 배치별 20MB 상한을 둔다. 성공한 배치의 해시는 프로젝트별로 로컬 ledger에 기록한다. 실패한 배치부터 재시도한다.

## 차량 앱의 공유 뉴스 조회

프로젝트 주소 수정 후 2026-11-13 실제 Supabase에 기사 2,290개를 업로드하고 REST count 조회로 확인했다.
Android의 기본 뉴스 목록은 `SupabaseNewsClient`를 사용한다. 앱에는 공개용 publishable 키만 포함된다.
서버 키는 Mac의 `.env`에만 두며 앱에 넣지 않는다.

최초 활성화는 `news_crawler/공유뉴스_앱연결.command`를 실행한다.
조회용 SQL이 미리 입력된 SQL Editor가 열린다. Run을 실행한 뒤 터미널에서 Enter를 누른다. 브라우저 자동 실행에 실패하면 출력된 링크를 직접 연다.
이어서 앱 로그인용 이메일/12자 이상 비밀번호를 정하면 Supabase Auth 데모 사용자와 허용 목록을 등록하고 실제 조회를 확인한다.
가입 확인 메일은 보내지 않는다. Auth 계정은 프로젝트 관리자의 Supabase 로그인 계정과 별개다.

앱은 사용자 토큰으로 `read_news` RPC만 호출한다. 로그인하지 않은 사용자와 허용 목록에 없는 사용자는 조회할 수 없다.
직접 테이블 접근과 쓰기 RPC는 앱 사용자에게 허용하지 않는다.
앱 로그인 정보/토큰은 메모리에만 두므로 앱 재시작/화면 재생성 시 다시 로그인한다.
로그인 후 액세스 토큰은 만료 전 또는 401 응답 시 갱신한다.
로그아웃은 서버 세션 종료를 시도하고 네트워크 실패 시에도 앱 내 토큰은 제거한다.
뉴스 화면이 활성화돼 있는 동안 5분마다 다시 조회하며, 백그라운드에서는 주기 조회를 중단하고 복귀 시 다시 조회한다.
조회 정렬은 발행시각 내림차순이고 URL 및 정규화 제목을 중복 제거한다. 분야별 최신 100건을 후보로 삼고 20건씩 표시한다.
클라우드 조회와 기존 로컬 조회의 제목 정규화/동점 처리와 분야 후보 제한은 완전히 동일한 구현이 아니다.

2026-11-13 조회용 SQL 적용과 데모 사용자 허용 목록 등록을 완료했다. 공개 키 + 사용자 토큰으로 총 후보 2,277건/조회 가능 485건, 사회 분야 필터 및 페이지 간 중복 없는 조회를 확인했다. Pleos 에뮬레이터 앱에서도 직접 로그인하고 같은 후보 건수와 실제 기사 표시를 확인했다. 데모 로그인 정보는 Git 제외 대상인 `news_crawler/.env.demo`에 소유자 전용 권한으로 저장한다.
현재 검증: APK 빌드/설치 성공, 에뮬레이터 클라이언트·토큰 갱신·권한 거부·체크포인트·뉴스 화면 테스트 14개 통과.
실제 Supabase 로그인 → read_news RPC → Pleos 앱 뉴스 표시까지 종단 간 확인했다. 맥을 켜둔 상태의 장시간 자동수집/갱신과 실차 검증은 별도다.
RSS 후보 선정은 AI 처리 권한이나 게시 승인을 부여하지 않는다. 본문·외부 AI 처리 권한 검사는 유지한다.
RSS 제목·설명은 외부 LLM 없이 별도 편성할 수 있으나, 일반 게시에는 출처별 TTS·재사용 허용 근거와 사람 승인이 필요하다.
현재 허용 근거는 미확보다. 명시적인 debug 비공개 미리보기만 허용하며 실제 DB 게시는 보류한다.
실행 절차는 [비공개 RSS 테스트](../backend/RSS_PREVIEW.md)를 참고한다.
PR #21/#23 이후 홈 브리핑은 익명 Auth 세션과 read_published_briefing RPC를 사용한다.
익명 가입·청취 기록 업로드·QR 생성은 쓰기 작업이므로 읽기 전용 검증에서는 실행하지 않는다.
비공개 RSS 테스트 기록은 별도 로컬 저장소에만 두고 클라우드 및 QR 공유를 차단한다.
LLM 결과, 리뷰 승인, 사용자 세션은 이번 클라우드 동기화 대상에 포함하지 않는다.

## 보관 및 전송 정책

`news_crawler/config.json`의 `cloud_storage`가 공유 DB 정책이다.

```json
"cloud_storage": {"retention_days": 5, "max_articles": 10000}
```

발행 시각 기준 최근 120시간의 기사 중 가장 최신 1만 개를 공유 DB 대상으로 삼는다.
같은 시각이면 URL 오름차순으로 정한다. 분야별 제한이 아닌 전체 기사 상한이다.
업로드를 성공한 뒤 REST DELETE로 발행 5일 경과분을 삭제하고, 다른 수집기가 추가한 자료까지 포함해 총량 초과분도 오래된 순으로 삭제한다.
기사 삭제 시 `news_memberships`는 기존 FK의 ON DELETE CASCADE로 정리한다.
사용자 계정·허용 목록·로컬 세션·OnePaper는 정리 대상이 아니다.
정리는 Mac 동기화 시 실행한다. Mac이 꺼져 있을 때 독립 실행되는 서버 예약 작업은 아니다.

내용/분야/출처의 SHA-256 해시가 같으면 전송하지 않는다. 반복 수집으로 바뀌는 `last_seen`만으로는 재전송하지 않는다.
따라서 클라우드 `last_seen`은 매 RSS 확인 시각을 항상 반영하지 않고 마지막 내용 전송 시의 값을 유지할 수 있다.
보관 기준은 `last_seen`이 아니라 `published_at`이므로 재수집으로 보관기간이 연장되지 않는다.
외부에서 DB를 비웠다면 `python3 shared_db.py --full`로 보관 대상 전체를 복구한다.
같은 Mac에서 두 자동수집이 겹치면 파일 잠금으로 클라우드 동기화는 하나만 실행한다.

2026-11-13 측정: 로컬 원본 2,290개, SQLite 약 5.31MiB, 기사 JSON 약 3.77MiB.
이는 PostgreSQL의 실제 인덱스·시스템 테이블 포함 사용량과는 다르다.
매번 전체를 전송하면 5분 간격 기준 기사 JSON만 하루 약 1.06GiB를 반복 전송하므로 변경분 동기화를 적용했다.
신규 수집이 초기 표본과 같다는 보장은 없으므로 1만 개 안전 상한을 병행한다.

실제 정책 적용 확인: 공유 DB 2,290 → 1,897건, 발행 후 5일 경과 393건 삭제, 경과분 잔여 0건.
동일 데이터 재동기화는 업로드 0건/정리 0건으로 성공했다. 로컬 원본은 2,290건 그대로다.
