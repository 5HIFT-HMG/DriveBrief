# 뉴스·AI 파이프라인 DB 통합

## 병합 기준

- main 8998188 (AI 알고리즘 v2 포함): AI 선정/편성, 품질 검사, TTS 타이밍, 앱 청취 기록/OnePaper.
- design/#7/newspaper-theme c248185: 신문 지면 디자인.
- 기존 로컬 작업: RSS 37개 피드, Supabase 공유 뉴스, 세션 API, 본문/권한 경계와 검토 파이프라인.

세 모듈 충돌은 통합했다. `ReviewStore.briefing(limit=None)`의 전체 풀 조회와 실제 기사용 클래스 설정을 모두 유지한다.
새 UI 디자인과 SessionHistory/SessionPaper는 유지하고 저장 어댑터를 추가했다.

## 최초 연결

1. 기존 news_crawler/.env에 프로젝트 URL과 서버 secret key가 있어야 한다. 이 파일은 Git 제외다.
2. news_crawler/파이프라인DB_연결.command를 실행한다.
3. 미리 입력된 SQL을 Run으로 실행한다. 적용 파일은 migrations/20261113_pipeline_storage.sql이다.
4. 터미널에서 Enter를 누르면 기존 검토 자료를 동기화한다. 새 요약을 생성하거나 승인하지 않는다.
5. 루트 run-local.command로 실행한다. 기존 자동수집/서버 프로세스는 종료하고 이 통합본을 실행한다.
6. 앱의 실제 뉴스 목록에서 데모 계정으로 로그인한 뒤 승인 브리핑/OnePaper를 이용한다.

## 공유 저장 구조

| 자료 | 저장 위치 | 접근 |
|---|---|---|
| RSS 기사/분야·출처 | news_articles/news_memberships | 기존 사용자 조회 RPC, 쓰기는 수집 서버 |
| 검토 입력/초안/승인/출처 | briefing_review_records | 서버 secret key만 접근, 앱에 원문/검토자 응답 안 함 |
| 청취 기록/OnePaper 스냅샷 | listening_history | 사용자·장치별 RPC, 직접 테이블 접근 차단 |

검토 레코드는 원래 JSON 문자열을 TEXT로 저장한다. JSONB 재정렬로 기존 revision/근거 검증이 달라지지 않도록 한다.
namespace fictional/real을 분리한다. 동기화는 업로드 ledger와 revision 조건 PATCH로 다른 검토자의 수정을 덮어쓰지 않는다.
충돌은 conflicts에 표시하며 로컬 검토 자료를 보존한다. 충돌한 초안을 자동 승인하거나 강제 덮어쓰기 하지 않는다.

기존 요약/검토 CLI로 작업한 결과는 서버의 다음 수집 주기에서 공유된다. 바로 보내려면 backend에서:

```sh
DRIVEBRIEF_SHARED_DB=1 .venv/bin/python -m drivebrief_api.shared_backend
```

다른 작업자의 DB 파일을 명시해서 보내려면:

```sh
.venv/bin/python -m drivebrief_api.shared_backend --db /path/to/review.sqlite3 --namespace fictional
```

공유 모드 API는 클라우드 승인 저장소를 읽고, 기존 검증/선정/시간 편성 코드를 그대로 통과시킨다.
DB 장애·잘못된 승인 데이터는 오류로 처리하고 미승인 데이터를 재생 가능 상태로 바꾸지 않는다.
실제 기사 경로는 기존 본문·권한·현재 원문 일치 검사까지 유지하므로 RSS 메타데이터만으로는 요약 재생되지 않는다.
`/v1/news/status`의 review_sync에서 마지막 검토 자료 동기화 결과를 볼 수 있다.

## 청취 기록

로그인 계정별 앱 저장소를 분리한다. 로그인 전 로컬 기록은 임의의 계정으로 업로드하지 않는다.
장치 UUID는 noBackupFilesDir에 저장하며 앱에는 비밀 키나 사용자 비밀번호/토큰을 영구 저장하지 않는다.
기존 SessionHistory 스냅샷을 로컬에 먼저 저장하고 2초간 변경을 모아 DB에 전송한다.
실패하면 로컬 기록을 보존하고 30초 후 재시도한다. OnePaper에 동기화 상태를 표시한다.
재로그인 시 같은 계정·장치의 클라우드 기록이 더 최신이면 복원하고, 클라우드에 없는 로컬 세션도 합쳐 최근 20개를 보존한다. 복원 중 새 로컬 이벤트가 발생하면 그 변경을 우선한다.
계정이 바뀐 뒤 이전 계정 기록을 새 사용자 토큰으로 업로드하지 않도록 소유자를 확인한다.

최근 20세션 제한을 유지한다. 클라우드 전송 스냅샷이 450KB를 초과하면 로컬에 보존하고 전송이 대기한다.
뉴스 5일 정리는 검토 기록이나 사용자 청취 이력을 삭제하지 않는다. 기사 삭제와 연결되는 FK도 만들지 않는다.
추가 저장소는 뉴스와 별개로 용량이 증가하므로 원문/검토 기록이 쌓이면 대시보드에서 관리해야 한다.

## 검증과 한계

로컬 통합: 백엔드 검증·선정·편성·리뷰·DB 충돌 테스트, Android 빌드/단위 테스트, 에뮬레이터 인증·계정 격리·저장 복원·UI 테스트.
실제 공유 뉴스 1,897건을 읽어 기존 랭킹 API가 응답하는 것을 확인했다.
2026-11-13 추가 저장 테이블 SQL 적용을 확인했다. 기존 검토 자료 3건을 실제 DB에 동기화하고 원본 문자열이 정확히 일치하는지 확인했다.
Git 저장소에는 팀원의 로컬 승인 DB와 API 키가 포함되지 않는다. 가져온 기존 로컬 검토 DB의 3건은 미승인 상태여서 자동 재생하지 않는다.
실제 청취 기록 저장/조회, 동일 요청 재전송, revision 갱신과 오래된 요청 거부, 익명 접근 차단, 두 번째 인증 계정의 타 사용자 기록 접근 차단을 확인했다. 검증용 기록과 임시 계정은 정리했다. 승인 취소 전파는 자동 테스트에서 검증했으며 실제 사용자 자료를 임의 승인/변경하지 않았다.
브리핑 편성 HTTP API는 기존 Mac 로컬 서버를 유지한다. 클라우드 DB 연동이 API 서버 배포를 대신하지 않는다.

최종 통합 검증: backend 123개, crawler 25개, Android JVM 10개, Pleos 에뮬레이터 24개 테스트 통과.
APK/테스트 APK 빌드·설치 및 실제 uvicorn /healthz HTTP 200 확인.
공유 뉴스 → 기존 랭킹의 실제 데이터 연결 및 신규 검토/청취 테이블의 실제 클라우드 저장·조회도 확인했다. 기존 검토 자료 3건은 미승인이므로 공유 승인 브리핑/편성 API가 HTTP 200과 빈 기사 목록을 반환하는 것까지 확인했다.
